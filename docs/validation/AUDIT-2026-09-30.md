## 판정

**기본 동기화는 실제로 작동하지만, 공개 배포 판정은 보류다.** 폴더 삭제의 충돌 누락, 종료 후 전송 복구, 로컬 저장의 원자성, 저장 실패의 성공 표시가 데이터 보존을 깨뜨린다. 기존 테스트 통과와 `docs/REPORT.md`의 구현 완료 선언으로 이 경로를 검증했다고 볼 수 없다.

대상은 `/Users/lesa/Desktop/Repo/shatsu-ren`, HEAD `e4db118`에 검사 시작 시 존재한 미커밋 변경을 포함한 작업 트리다. 제품 소스 수정·커밋·배포는 하지 않았다. 이 검사에서 추가한 것은 재현 테스트 두 파일과 이 보고서, 합성 데이터 화면 증거다. 개인 북마크와 개인 계정을 시험 데이터로 사용하지 않았다.

P1은 공개 전 우선 수정해야 할 데이터 보존/경계 오류, P2는 그 다음에 수정할 동작·성능·검증 문제다. **재현**은 실행으로 확인, **코드 확인**은 해당 분기와 호출 경로를 읽어 확인한 것이며 전체 브라우저 시나리오를 실행했다는 뜻은 아니다.

## P1 발견 사항

### F01. 폴더 삭제가 다른 브라우저의 하위 수정까지 충돌 없이 삭제한다 — 실제 두 브라우저 재현

위치: `apps/extension/src/sync/reconcile.ts:541`, `apps/extension/src/sync/engine.ts:818`.

A와 B가 동일한 폴더/자식을 동기화한 뒤 자동 동기화를 끈다. A가 폴더를 삭제하고 B가 자식을 수정해 서버에 보낸다. 이후 A가 동기화하면 자식의 새 수정이 휴지통으로 들어가고 활성 snapshot에서 사라진다. A의 충돌 건수는 0이다.

삭제 판단은 폴더 자체의 revision만 비교한다. 자식 수정은 폴더 revision을 올리지 않으며, 삭제 RPC의 digest는 사용자가 마지막으로 확인한 subtree가 아니라 **방금 받은 서버 shadow**로 만든다. 따라서 서버의 digest 검증도 이 삭제를 허용한다. 원격 추가·하위 수정까지 포함해 마지막 합의 상태와 비교하고, 변화가 있으면 삭제 검토로 보내야 한다.

증거: `AUD-04`, `BROWSER-AUD-01`. 실제 Chromium/Aside, 실제 bookmarks API와 Supabase RPC로 재현했다. 휴지통의 30일 복원 가능성은 확인되지만 충돌 보호 실패가 없어지는 것은 아니다.

### F02. 종료 시 in_flight로 남은 전송이 다시 실행되지 않는다 — 재현

위치: `apps/extension/src/sync/engine.ts:845`, `apps/extension/src/sync/engine.ts:690`.

push는 전송 전에 outbox 상태를 `in_flight`로 저장하지만 다음 실행은 `pending`만 읽는다. 정상 catch는 pending으로 돌리지만 worker 강제 종료에는 catch가 실행되지 않는다. 시작 복구에는 outbox 회수/receipt 조회가 없다. 동일한 opId를 안전하게 재전송할 수 있는 서버를 만들었어도 클라이언트가 그 재전송을 하지 않는다.

증거: `AUD-01`. 종료 후 가능한 저장 상태를 실제 IndexedDB API의 테스트 구현에 넣고 새 엔진으로 실행했을 때 RPC 호출 0회, 상태는 계속 in_flight였다. 실제 OS 강제 종료를 주입한 검사는 아니다.

### F03. 신규 mapping과 outbox가 서로 다른 transaction에 저장된다 — 재현

위치: `apps/extension/src/sync/engine.ts:337`, `apps/extension/src/sync/engine.ts:391`, `apps/extension/src/sync/reconcile.ts:339` 부근.

새 로컬 항목에 revision 0 mapping을 먼저 저장하고, native 적용과 다른 binding 처리까지 끝난 뒤 outbox를 저장한다. 사이에 종료/저장 실패가 있으면 mapping만 남는다. 다음 reconcile은 revision 0을 이미 생성 대기 중인 항목으로 보류하지만 실제 전송 작업은 없다. 의도를 재구성하거나 mapping과 의도를 같은 transaction으로 확정해야 한다.

증거: `AUD-07`. outbox가 없는 revision 0 항목이 held 1, 전송 0 상태로 남았다.

### F04. native create 완료와 mapping 저장 사이 종료가 중복을 만든다 — 재현

위치: `apps/extension/src/sync/engine.ts:561`, `apps/extension/src/sync/engine.ts:692`.

native create 직후 journal을 done으로 저장하고 그 다음 observed mapping을 쓴다. mapping 저장 전 종료하면 `resultLocalId`를 알고 있는 done journal이 남지만 recoverJournal은 started만 읽는다. 기존 항목은 새 로컬 항목으로, 같은 원격 항목은 원격 전용 항목으로 판단해 또 생성한다. journal 완료와 mapping을 같은 transaction으로 확정하고 이 저장 상태를 시작 복구가 처리해야 한다.

증거: `AUD-02`. done journal/resultLocalId/native 항목이 있고 mapping만 없는 상태에서 native create가 다시 호출되어 항목 수가 늘었다. 청사진 D01의 합격 조건에 어긋난다.

### F05. 한 번 해결한 항목의 다음 충돌이 화면에 나타나지 않는다 — 재현

위치: `apps/extension/src/sync/engine.ts:341`.

충돌 ID가 collectionId/globalId로 고정이고 기존 레코드가 있으면 새 충돌을 쓰지 않는다. resolved 레코드도 이 조건에 걸린다. 같은 북마크에 두 번째 동시 수정이 발생하면 새 충돌이 계산돼도 open 충돌은 0이고 해당 변경이 진행되지 않는다. 해결된 충돌을 재개하거나 충돌 발생별 ID를 사용해야 한다.

증거: `AUD-06`. resolved 충돌이 있는 동일 항목에 local/remote의 서로 다른 수정을 넣어도 open 레코드가 생기지 않았다.

### F06. 로그아웃/계정 변경 중 이미 시작한 native 적용을 중단하지 못한다 — 재현

위치: `apps/extension/src/sync/engine.ts:533`, `apps/extension/src/service.ts:417`.

logout은 epoch를 바꾸지만 applyLocal의 각 create/update/move/remove 전에는 epoch 확인이 없다. binding 전체 처리가 끝나서야 확인한다. 따라서 로그아웃이나 계정 전환이 진행되는 동안 이전 계정의 여러 native 변경이 계속 실행될 수 있다. 충돌 해결·import 등 엔진 밖 native 경로에도 같은 실행 경계가 필요하다.

증거: `AUD-05`. 첫 native create에서 epoch를 바꿨는데 두 번째 create도 실행됐다. 계정 A/B 전체 UI 전환을 실행한 검사는 아니며 중단 경계의 실패를 재현했다.

### F07. 연결 해제 후 ‘대기 변경 보관’한 작업이 계속 전송된다 — 재현

위치: `apps/extension/src/service.ts:626`, `apps/extension/src/sync/engine.ts:847`.

disconnectBinding은 binding을 지우고 keep 선택 시 pending outbox를 남긴다. push는 존재하는 비활성 binding만 제외하므로 **binding이 아예 없는 collection의 작업은 허용**한다. 이후 수동/다른 폴더/alarm 동기화에서 해제한 폴더의 의도가 서버에 전송된다. 활성 binding을 명시적으로 허용하는 조건이 필요하다.

증거: `AUD-03`. 연결을 해제한 뒤 해당 collection의 applyOne이 호출됐다.

### F08. 저장 공간 부족을 INTERNAL로 처리하고 화면은 idle로 표시한다 — 재현

위치: `apps/extension/src/storage/db.ts:102`, `apps/extension/src/sync/engine.ts:123`, `apps/extension/src/service.ts:316`.

StorageError/must helper가 있지만 실제 저장 호출은 이 변환 경로를 사용하지 않는다. 원래 QuotaExceededError는 INTERNAL로 기록되고, 대표 상태 계산은 이 오류를 차단으로 취급하지 않는다. 대기가 아직 기록되지 않은 시점이면 화면이 최신 상태가 된다. 저장 경계에서 실패를 분류하고 저장 실패 후 native 변경과 성공 표시를 막아야 한다.

증거: `AUD-15`. observed transaction에 QuotaExceededError를 주입해 엔진 outcome=error, lastError=INTERNAL, 화면 snapshot status=idle을 확인했다. 실제 디스크를 가득 채우지는 않았다. 청사진 D08/U03 실패다.

### F09. 서버 RPC가 필수 동시성 검증값 누락을 허용한다 — 실제 DB 재현

위치: `supabase/migrations/20260929000000_shatsu_core.sql:357`, `:451`, `:455`.

patch/delete의 baseRevision, delete의 expectedSubtreeDigest가 없으면 SQL 비교가 NULL이 된다. PL/pgSQL IF는 이 값을 참으로 취급하지 않아 충돌 검사를 통과한다. 실제 RPC에 이 필드를 빼고 보낸 patch와 subtree delete 모두 applied였다. 클라이언트 zod schema는 직접 RPC 호출의 서버 검증을 대신하지 못한다.

필수 필드 존재/타입/범위 검사와 NULL에 안전한 비교가 필요하다. move/reorder/patchCollection 등 같은 비교 방식도 함께 점검해야 한다. **다른 계정 접근이 뚫렸다는 뜻은 아니다.** 소유권 검사는 별도 DB 테스트에서 통과했으며, 이 재현은 자기 계정의 CAS/삭제 보호를 우회한 것이다.

증거: `DB-AUD-01`. 삭제 후 활성 snapshot에서 두 항목이 사라지고 휴지통 itemCount=2를 확인했다.

### F10. 충돌 선택 적용 전에 서버/로컬을 새로 확인하지 않는다 — 재현 및 코드 확인

위치: `apps/extension/src/service.ts:661`.

resolveConflict는 cached shadow와 충돌의 과거 local 값을 신뢰해 native update/create/delete를 먼저 한다. 다음 pull은 그 뒤다. 충돌 화면을 열어 둔 사이 로컬 또는 서버가 바뀌면 이전 선택 내용으로 최신 native 변경을 덮거나 오래된 내용을 복제할 수 있다. `:669`의 재확인 조건도 삭제 상태가 달라진 경우를 놓친다. 선택 확정 시 최신 양쪽 상태를 확인하고 달라지면 재확인을 요구해야 한다.

증거: `AUD-14`에서 fresh pull보다 native update가 먼저 호출됐다. 실제 브라우저에서 화면을 오래 열어 둔 추가 경쟁은 실행하지 않았다.

### F11. 서버 복원 복구가 비교 미리보기 없이 이전 의도를 재전송한다 — 재현

위치: `apps/extension/src/service.ts:1097`.

recoverGeneration은 기존 outbox의 generationId를 바꾸고 snapshot을 받아 즉시 force sync한다. 의도와 복원된 서버를 비교해 새 계획을 승인받는 단계가 없다. 복원된 항목에 오래된 수정/삭제가 제출되거나 누락된 collection에 대한 작업이 실패할 수 있다. 이전 세대의 의도를 자동으로 새 세대 요청으로 바꾸기 전에 검토가 필요하다.

증거: `AUD-10`. recovery 호출 중 이전 outbox의 RPC 제출을 확인했다. 이 테스트는 RPC 경계를 mock한 것으로 복원된 실제 DB에서 성공한 변경을 주장하지 않는다. 청사진 D06의 ‘미리보기 복구’가 빠졌다.

### F12. 새 로컬 폴더 연결의 중첩/중복 검증과 병합 확정 경계가 부족하다 — 재현 및 코드 확인

위치: `apps/extension/src/service.ts:502`, `:561`, `apps/extension/src/sync/plan.ts:288`.

previewMerge와 달리 previewNewLocalFolder는 이미 연결된 collection과 부모의 binding 중첩을 확인하지 않는다. 기존 연결 아래에 다른 collection을 받으면 두 binding이 겹칠 수 있다. 이미 연결된 collection을 다시 받는 요청은 commitPlan의 bindings.put으로 기존 연결을 덮는다. UI에서 목록을 제한해도 백그라운드 요청 경계에 검증이 필요하다.

증거: `AUD-12`가 이미 연결된 collection/기존 root를 부모로 하는 요청을 허용했다. 실제 binding 덮어쓰기까지 실행한 검사는 아니다.

또한 applyMerge는 백업/최종 fingerprint 검사 전에 서버 collection 또는 native 폴더를 생성한다. commitPlan은 cached headSeq만 비교하고, 새 collection 생성 경로는 계획의 headSeq를 최신 값으로 바꾼다. 메모리 계획은 worker 종료 시 사라지고 createCollection 재시도에는 새 opId가 발급된다. 계획 재검증·백업·승인된 계획 영속화 후 같은 opId/journal로 적용하도록 순서를 정리해야 한다. 백업 실패 시 변경 없음과 종료 후 재개 조건을 새로 검증해야 한다.

추가로 확인한 경로:

- **런타임 순서 충돌:** `reconcile.ts:704`는 양쪽 모두 순서를 바꿔도 서버 순서를 덮어쓴다. DECISIONS D-013에 적혀 있지만 청사진의 초기 병합 순서 정책을 일반 런타임 충돌까지 넓힌 것이다. 사용자가 변경한 순서를 조용히 잃는 선택이므로 합의된 제품 정책/검토가 필요하다. 코드 확인.
- **서버 깊이 한도:** op_move는 폴더일 때만 subtree 깊이를 확인하고 op_restore에는 깊이 검사가 없다. 깊은 부모로 북마크 이동/폴더 복원에서 maxDepth=32를 지키는 경로가 부족하다. 코드 확인, 실제 한도 넘김 RPC는 미실행.
- **Realtime 권한:** `shatsu_core.sql:826`의 구독 정책 함수는 device/JWT session_id를 확인하지만 `session_valid()`를 부르지 않는다. 폐기된 Auth 세션의 유효기간 내 JWT는 RPC 읽기와 구독 판정이 다를 수 있다. 현재 broadcast는 본문 없는 changed 신호이므로 북마크 본문 유출로 단정하지 않는다. 코드 확인, 해당 폐기 세션의 실제 subscribe는 미실행.
- **공용 DB migration:** `shatsu_core.sql:888`은 public 스키마의 모든 함수 권한을 회수한다. 기존 Supabase 프로젝트의 다른 서비스 함수에도 영향을 줄 수 있다. 프로젝트가 소유한 함수만 대상으로 제한해야 한다. 코드 확인.
- **보존 운영:** purge 스케줄은 pg_cron이 이미 설치된 경우에만 생긴다(`:909`). 스케줄 설치/실패 알림을 검증하는 절차가 없어 30일 정리를 자동으로 보장할 수 없다. 운영 DB 검증이 필요하다.
- **UI 실패 처리:** useWorkerState의 error를 App이 사용하지 않아 상태 조회 오류가 계속 로딩/이전 화면으로 남을 수 있다. no-backend 온보딩에는 개인 backend 설정으로 가는 링크가 없다. 일부 표 제목은 영어 하드코딩이다. 코드 확인. 화면의 주요 기능은 아래 실제 브라우저 검사에서 확인했다.
- **릴리스 checksum:** pnpm zip은 ZIP만 재생성하고 기존 .sha256을 갱신하지 않는다. 이번 ZIP SHA-256은 `82f8842620087d09f998969874dd36cf11925352b982e1625899c5cff3db6956`, 남아 있던 파일은 `242b0235fd07772aae7fbd1684475492008a9f3693925187d3a8beefb8a4a4a1`이었다. 패키징 과정에서 checksum을 같이 만들도록 해야 한다. 실행 확인.
- **테스트 실행 안정성:** 마지막 Aside 반복 실행에서 60초 launch timeout 후 retry가 필요했고 최종 검사는 통과했다. `tests/lib/browser.ts:43`의 Promise.race는 timeout 시 진행 중 launch를 취소/정리하지 않는다. 실패/timeout 정리를 추가해야 한다. 종료 후 감사용 브라우저 프로세스가 남지 않은 것은 확인했다.

## 성능 해석

합성 데이터의 **변경 없는 단일 폴더 reconcile 계산만** 1k/10k 각각 5회 측정했다. 처음 독립 실행의 중간값은 9.27/126.73 ms였다. 이후 반복에서 중간값은 1k 12.52~32.67 ms, 10k 153.19~1645.78 ms로 변했고 10k 단일 최대값 4858.84 ms가 나왔다. JIT/GC/병행 프로세스 등 실행 조건을 통제한 성능 인증이 아니므로 한 숫자로 목표 통과를 판정하지 않는다.

분명한 구조 문제는 F15의 전체 배열 조회/멤버십 반복이다. 10k 정렬 경로에는 최대 약 1억 항목 분량의 native 조회 응답이 생길 수 있다. 실제 10k 브라우저 전체 적용과 메모리/유휴 CPU 측정이 필요하다.

새 브라우저 검사에서 단일 Aside→Chromium 생성 전달은 반복 실행별 274/267/318 ms였다. localhost의 소수 샘플이며 p95나 운영 서버 지연으로 주장하지 않는다. 양방향 최초 연결/수신은 별도로 통과했다. 과거 문서의 60회 p95 자료는 과거 자료로만 취급했다.

## 청사진·기존 완료 보고서 대조

- D01/D03의 종료 내구성은 F02~F04 때문에 현재 합격이라고 할 수 없다.
- D06은 generation mismatch의 서버 차단 코드와 ‘미리보기 복구’를 구분해야 한다. 복구 미리보기는 F11에서 빠져 있다.
- D08/U03은 F08로 실패가 재현됐다. StorageError 클래스가 존재하는 것만으로 구현됐다고 볼 수 없다.
- B07/U06/U07은 연결 검증·백업 순서·메모리 계획 소실을 새로 검증해야 한다.
- C03/C04는 첫 충돌뿐 아니라 해결 후 같은 항목의 반복 충돌과 늦은 선택 적용을 검증해야 한다.
- U08은 자동 동기화 off 상태에서의 durable 대기를, C13은 범위 밖 검토 선택 후 실제 결과를 확인해야 한다.
- P01/P02는 `PERFORMANCE.md`에 placeholder, `RESULTS.md`에 미확정 값이 남는다. 1k/10k 실제 적용과 30분 유휴는 별도 인증이 필요하다. 현재 root E2E 명령도 F20 때문에 증거가 아니다.
- Google Chrome 브랜드 빌드와 Google OAuth는 Chromium dev 비밀번호 로그인으로 대체 검증하지 않았다. Aside Google OAuth도 이번 검사에서 실행하지 않았다.

기존 정상 경로에는 scoped DB, 서버 소유권 검사, 워크스페이스 lock, opId/body receipt 멱등성, tombstone/휴지통, 응답 schema 검증, popup의 worker 메시지 구조 등 유효한 기반이 있다. 새 플랫폼이나 더 복잡한 아키텍처로 바꿀 이유는 없다. 현재 상태 전이와 영속화 경계를 먼저 고치는 편이 작고 확실하다.

## 재실행

프로젝트 루트에서 실행한다. 로컬 Supabase는 이미 시작돼 있어야 하며 **개인 데이터가 있는 DB에 reset을 실행하지 않는다.**

```sh
pnpm --filter shatsu-ren-extension exec vitest run src/audit-20260930.test.ts --disable-console-intercept

# 제품의 기존 dev 빌드와 구분되는 임시 감사 빌드
SHATSU_DEV_AUTH=1 pnpm --filter shatsu-ren-extension exec node --input-type=module -e 'import {build} from "wxt"; await build({mode:"development",outDir:".output-audit"});'
pnpm --filter shatsu-ren-tests exec vitest run audit/runtime.test.ts --disable-console-intercept --no-file-parallelism

# 개인 계정까지 바꾸는 전역 작업 두 가지를 제외한 기존 DB 검사
pnpm --filter shatsu-ren-tests exec vitest run db/rpc.test.ts -t '^(?!.*D06)(?!.*purge_expired).*'
supabase test db
```

감사 runtime은 매번 합성 계정과 임시 브라우저 프로필을 만들며 자신이 만든 합성 계정만 종료 후 삭제한다. native/RPC mock 종료 상태 재현과 실제 브라우저 재현을 혼동하지 않는다.

화면 증거: `docs/validation/audit-20260930/chromium-overview.png`, `aside-overview.png`. 정상 상태의 개요 화면만 확인했으며 전체 화면의 접근성 인증은 아니다.
