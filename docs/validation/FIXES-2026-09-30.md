# 공유와 삭제 보호 수정 결과 — 2026-09-30

같은 shatsu-ren 계정에 연결된 Chromium/Aside에서 추가·수정·이동이 자동으로 공유된다. 삭제는 한 항목이라도 발신과 수신 각각 검토를 거친다. 삭제 검토는 다른 항목의 공유를 멈추지 않는다. 개인 북마크를 시험 데이터로 사용하지 않았고, 로컬 DB 초기화나 전역 데이터 정리를 실행하지 않았다.

이 문서는 수정 후 결과다. `AUDIT-2026-09-30.md`는 수정 전 재현 기록으로 보존했다. 작업은 로컬 구현·검증·ZIP 생성까지이며 커밋, 공개 업로드, 운영 배포는 하지 않았다.

## 관찰한 공유·삭제 흐름

1. 두 브라우저에서 같은 계정으로 로그인하고 공유 폴더를 연결한다.
2. 어느 쪽에서 추가하거나 수정해도 상대의 실제 bookmarks API에 반영된다.
3. 로컬에서 삭제하면 서버 전송을 보류하고 삭제 대상 목록을 보여 준다. 다른 브라우저에서 추가한 항목과 하위 수정도 이 목록에 포함된다.
4. 목록을 연 뒤 내용이 바뀌면 기존 승인을 거부하고 최신 목록으로 다시 검토한다. 삭제한 로컬 폴더 아래로 원격 항목이 추가되면 서버와 검토 목록에 보존하며, 존재하지 않는 로컬 부모에 생성을 시도하지 않는다.
5. 발신 승인을 마쳐도 상대 브라우저의 실제 삭제는 수신 승인 전까지 보류한다. 삭제 전 백업과 휴지통 복원을 실제로 확인했다.

추가로 동시 순서 변경을 명시적 충돌로 보여 주며, 전송 도중 다시 바뀐 순서가 receipt 처리에서 사라지지 않게 했다. 같은 프로필의 Realtime 연결·해제를 직렬로 처리하고, 오래된 계정의 연결 요청을 epoch로 차단한다. 이 경로의 회귀 시험도 통과했다.

## 측정과 증거

- 양방향 각 30회 추가: A→B p95 270ms, B→A p95 269ms, 감지한 신호 누락 0. 마지막 삭제 보호 실행의 B→A 추가는 273ms.
- 실제 1,000개 공유: 미리보기 34ms, 업로드 1,496ms, 상대 수신 1,325ms, 49개 순서 변경 609ms.
- 변경 없는 10,000개 순수 비교는 로컬 반복 측정 중앙값 약 5–8ms. 이는 native API/네트워크를 포함한 전체 동기화 시간이 아니다.
- 기존 1,000개 순서 확인은 native 자식 조회 1회, 실제 이동 0회로 회귀 검증했다.
- 브라우저 버전은 두 시험 환경 모두 Chromium 153 계열이다. 자동화의 Chrome 쪽은 Playwright Chromium이며 Google Chrome 개인 프로필을 의미하지 않는다.
- 합성 데이터 화면은 `audit-20260930/manual-review-before.png`, `manual-review-after.png`, `aside-deletion-approved.png`에 있다. 원시 측정은 `raw/r01-latency.json`, `raw/p01-1k.json`, `raw/recovery-e2e-log.json`에 있다.
- SQL red/green 및 안전한 migration 적용 증거는 `.omo/evidence/server-safety/README.md`에 정리했다.

## 검증 범위와 한계

Google OAuth 실제 로그인, 운영 서버 배포, Google Chrome 브랜드 빌드의 수동 설치, Edge, 수정 후 31분 유휴, native 10k 전체 전송은 검증하지 않았다. 시험은 합성 개발 계정과 임시 프로필로 진행했다. 이전 설치가 삭제한 다른 앱의 SQL grant는 자동 추정하여 복원하지 않는다.

Chrome bookmarks API는 원자적 subtree 비교·삭제 기능을 제공하지 않는다. 삭제 직전 재검사와 백업으로 보호하지만 이미 시작한 단일 native 호출을 계정 전환으로 취소할 수는 없다. 실패·미해결 기록과 import checkpoint는 보존되어 누적될 수 있다.

최종 자체 검토에서는 삭제 승인/백업/재확인 순서, 중단 복구와 opId, 계정 실행 경계, 입력 검증, SQL migration의 데이터 비변경, 테스트의 실패 조건을 다시 읽었다. 새 의존성을 추가하지 않았다.
